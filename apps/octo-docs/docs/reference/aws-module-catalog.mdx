title: AWS Module Catalog
---

`@quadnix/octo-aws-cdk` is our own implementation layer for AWS. It is a usable library, and it is a
worked example of how to build one: every module in it is written with the same pieces described in
[Anatomy of a Module](/docs/building-modules/anatomy-of-a-module), and nothing in it is privileged
by the framework. A region module you write yourself sits alongside these on equal terms.

That matters when reading this page. What follows is a set of answers one team gave to questions
like "what is a region made of", not the answers. Where a module does not fit your account layout,
the move is to write your own and keep the rest.

Each entry lists what a caller passes and what appears in AWS. The generated API documentation has
every input in full.

## Apps and accounts

An app produces no cloud resources. An account decides which credentials to use and which provider
block is rendered, and produces none either. Those credentials are also what Octo authenticates with
where it calls AWS itself rather than through Terraform, which today is the image publishing below.

| Module                        | Inputs                                          | Creates |
|-------------------------------|-------------------------------------------------|---------|
| `SimpleAppModule`             | `name`                                          |         |
| `AwsIniAccountModule`         | `accountId`, `app`, `iniProfile?`, `endpoints?` |         |
| `AwsCredentialsAccountModule` | `accountId`, `app`, `credentials`, `endpoints?` |         |
| `AwsLocalstackAccountModule`  | `app`, `endpoints?`                             |         |
| `AwsMotoAccountModule`        | `app`, `endpoints?`                             |         |

`AwsIniAccountModule` reads a named profile from `~/.aws/credentials`, which is what the templates
use. `AwsCredentialsAccountModule` takes credentials directly, for CI. The Localstack and Moto
modules point the provider at a local emulator, and exist for testing.

```yaml
imports:
  - className: AwsIniAccountModule
    importPath: "@quadnix/octo-aws-cdk/modules/account/aws-ini-account"
```

Every import path follows that shape: the package, then `modules/<model-type>/<module-name>`.

## Regions and subnets

| Module                      | Inputs                                                                                                                        | Creates                                                                         |
|-----------------------------|-------------------------------------------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------|
| `AwsSingleAzRegionModule`   | `account`, `name`, `regionId`, `vpcCidrBlock`                                                                                 | VPC, internet gateway                                                           |
| `AwsMultiAzRegionModule`    | `account`, `name`, `regionIds`, `vpcCidrBlock`                                                                                | VPC, internet gateway                                                           |
| `AwsServerlessRegionModule` | `account`, `name`, `regionId`                                                                                                 |                                                                                 |
| `AwsSimpleSubnetModule`     | `region`, `subnetName`, `subnetCidrBlock`, `subnetAvailabilityZone`, `subnetOptions?`, `subnetSiblings?`, `localFilesystems?` | subnet, route table, network ACL, security group, NAT gateway, EFS mount target |

Both region modules define a region as one VPC with an internet gateway. They differ in what the
region publishes: a single-AZ region advertises one availability zone, a multi-AZ region advertises
several, and that is what a subnet module reads when deciding where it can place itself. Their
region IDs are Octo's own, `aws-eu-west-1a`, distinct from the AWS region.

`AwsServerlessRegionModule` is a region with no network: it creates nothing, and says only which AWS
region its services are created in, as `aws-us-east-1`. It publishes a different shape from the
other two, so a subnet or anything else that needs a VPC refuses it when the modules are composed.
The static website sits in one, and a storage bucket takes a region of any of the three kinds.

The subnet module is where the network shape actually lives. `subnetOptions` carries
`createNatGateway`, `disableSubnetIntraNetwork`, and `subnetType`; `subnetSiblings` is how a private
subnet asks to route through a public one's NAT gateway.

:::info[A NAT gateway costs money by the hour]
`createNatGateway: true` is the one input in this catalog with an ongoing bill attached, whether or
not anything is running behind it.
:::

## Servers, deployments, and executions

| Module                    | Inputs                                                                                                                                | Creates                                      |
|---------------------------|---------------------------------------------------------------------------------------------------------------------------------------|----------------------------------------------|
| `AwsEcsServerModule`      | `account`, `serverKey`, `s3?`, `securityGroupRules?`                                                                                  | IAM role                                     |
| `AwsEcsDeploymentModule`  | `server`, `deploymentTag`, `deploymentContainerProperties`                                                                            |                                              |
| `AwsEcsEnvironmentModule` | `region`, `environmentName`, `environmentVariables?`                                                                                  | ECS cluster                                  |
| `AwsEcsExecutionModule`   | `deployments`, `environment`, `subnet`, `executionId`, `desiredCount`, `environmentVariables?`, `filesystems?`, `securityGroupRules?` | ECS service, task definition, security group |

These four are one story told in four parts. A server is the logical microservice and gets an IAM
role. A deployment is one version of its container. An environment is a stage inside a region, and
becomes the ECS cluster. An execution is a deployment running in an environment in a subnet, and is
what actually runs.

`AwsEcsServerModule`'s `s3` input is the shop's receipts grant from [Shop
Stack](/docs/getting-started/shop-stack): a list of storage services and, per service, the
access prefixes the server may access with `READ`, `WRITE`, or `READ_WRITE`. That produces an
[overlay](/docs/fundamentals/overlays), a policy on the role, and a statement on the bucket.

Three of the inputs above are nested objects rather than scalars, and each one is a shape a
definition file has to get right before anything is written. A deployment describes the container
image the task definition registers:

```yaml
  - moduleId: checkout-deployment-v1-module
    moduleClass: AwsEcsDeploymentModule
    moduleInputs:
      server: "${{checkout-server-module.model.server}}"
      deploymentTag: 0-0-1
      deploymentContainerProperties:
        cpu: 256            # 256, 512, 1024, 2048, 4096, 8192, or 16384
        memory: 512         # MiB
        image:
          command: /bin/sh
          ports:
            - containerPort: 80
              protocol: tcp
          uri: "${env.CHECKOUT_IMAGE_URI}"
```

`deploymentTag` is two to thirty-two characters of letters, numbers, hyphens, and underscores. A dot
is not one of them, so a version reads as `0-0-1`.

An execution names one main container and any sidecars, each pairing a deployment with the container
properties that deployment runs under:

```yaml
  - moduleId: checkout-v1-staging-execution-module
    moduleClass: AwsEcsExecutionModule
    moduleInputs:
      executionId: checkout-v1-staging
      desiredCount: 1
      environment: "${{staging-environment-module.model.environment}}"
      subnet: "${{public-subnet-module.model.subnet}}"
      deployments:
        main:
          containerProperties:
            image:
              command: /bin/sh
              essential: true
              name: checkout-v1
              ports:
                - containerPort: 80
                  protocol: tcp
          deployment: "${{checkout-deployment-v1-module.model.deployment}}"
        sidecars: [ ]
```

`securityGroupRules` is optional, and leaving it out gives the execution one egress rule allowing
all outbound traffic, which is what AWS gives a security group you create by hand. A Fargate task
has to reach ECR to pull the image it runs, so an execution that could reach nothing could never
start. Declare an egress rule of your own and that default is not added, because you have said what
this execution may reach:

```yaml
      securityGroupRules:
        - CidrBlock: 10.0.0.0/16
          Egress: true
          FromPort: 443
          IpProtocol: tcp
          ToPort: 443
```

The image URI in `deploymentContainerProperties` is written out rather than referenced. A task
definition and the image module that publishes to it sit on either side of a reference Octo does not
resolve, so the URI is assembled by hand from the account, the region, the repository, and the tag,
and declared as one `env` key because a `${env.KEY}` reference resolves only as a whole value:

```yaml
env:
  - key: CHECKOUT_IMAGE_URI
    kind: string
    value: "123456789012.dkr.ecr.eu-west-1.amazonaws.com/shop/checkout:0.0.1"
```

The repository is `<imageFamily>/<imageName>` from `AwsEcrImageModule`, and the tag is `imageTag`
from `AwsEcrImageTagModule`. Declaring the version and the stack that runs it in one definition file
means one apply publishes the image and registers the task definition that names it.

## Services

| Module                                   | Inputs                                                                                                                                                                                                            | Creates                                                                                                                                                  |
|------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------|
| `AwsS3StorageServiceModule`              | `region`, `bucketName`, `accessPrefixes?`, `blockPublicAccess?`, `directoryPath?`, `filter?`, `transform?`, `subDirectoryOrFilePath?`                                                                             | S3 bucket, public access block, bucket policy, and with `directoryPath` one object per file                                                              |
| `AwsS3StaticWebsiteServiceModule`        | `region`, `bucketName`, `directoryPath`, `filter?`, `transform?`, `subDirectoryOrFilePath?`                                                                                                                       | S3 bucket, public access block, bucket policy, website configuration, one object per file                                                                |
| `AwsDynamoDBServiceModule`               | `region`, `TableName`, `KeySchema`, `AttributeDefinitions`, `billingMode`, `GlobalSecondaryIndexes?`, `LocalSecondaryIndexes?`, `StreamSpecification?`, `timeToLiveAttribute?`                                    | DynamoDB table                                                                                                                                           |
| `AwsDynamoDBGlobalServiceModule`         | `dynamoDBService`, `replicas`                                                                                                                                                                                     | DynamoDB global table replicas                                                                                                                           |
| `AwsEcsAlbServiceModule`                 | `region`, `albName`, `listeners`, `subnets`, `targets?`                                                                                                                                                           | application load balancer, listener, target group, security group                                                                                        |
| `AwsCloudFrontServiceModule`             | `account`, `distributionName`, `origins`, `routes`, `aliases?`, `certificateArn?`, `defaultRootObject?`, `errorResponses?`, `priceClass?`, `cachePolicies?`, `originRequestPolicies?`, `responseHeadersPolicies?` | CloudFront distribution, an origin access control per bucket it serves, a statement in each of those buckets' policies, and the custom policies declared |
| `AwsCloudFrontInvalidationServiceModule` | `cloudFront`, `source`                                                                                                                                                                                            | an invalidation of the distribution every time the bucket's files change                                                                                 |

`AwsS3StaticWebsiteServiceModule` makes a public bucket that answers on its S3 website endpoint,
over plain HTTP. A site served over HTTPS from a closed bucket is two modules instead:
`AwsS3StorageServiceModule` holds the files, and `AwsCloudFrontServiceModule` serves them. Which
module you pick is what decides whether the bucket is public, so removing a distribution can never
reopen a bucket behind it.

`AwsCloudFrontServiceModule` sits under the account, because a distribution is not in any one
region. `origins` names what it serves, each one an `originId` and a `source`; today a source is a
bucket from `AwsS3StorageServiceModule`. `routes` sends requests to an origin by its `originId`. The
route with no `pathPattern` is the default, and the others are matched in the order they are given.
For every bucket it serves, the module adds a statement to that bucket's policy naming the
distribution, so the bucket stays closed to everyone else.

```yaml
  - moduleId: website-storage-module
    moduleClass: AwsS3StorageServiceModule
    moduleInputs:
      bucketName: my-website-bucket
      directoryPath: website
      region: "${{region-module.model.region}}"

  - moduleId: website-cloudfront-module
    moduleClass: AwsCloudFrontServiceModule
    moduleInputs:
      account: "${{account-module.model.account}}"
      defaultRootObject: index.html
      distributionName: my-website
      errorResponses:
        - errorCode: 403
          responseCode: 404
          responsePagePath: /error.html
      origins:
        - originId: website
          source: "${{website-storage-module.model.service}}"
      routes:
        - originId: website

  - moduleId: website-invalidation-module
    moduleClass: AwsCloudFrontInvalidationServiceModule
    moduleInputs:
      cloudFront: "${{website-cloudfront-module.model.service}}"
      source: "${{website-storage-module.model.service}}"
```

A bucket served this way cannot have a dot in its name. The distribution reaches it at
`<bucket>.s3.<region>.amazonaws.com` over HTTPS, and the certificate AWS serves there covers a
single label, so a dotted name is refused when the modules are composed rather than answering `502`
to every visitor later.

Set `aliases` to answer on your own domains and `certificateArn` to a certificate covering them;
CloudFront reads certificates from `us-east-1` alone, wherever the bucket lives. The DNS records
pointing at the distribution are yours to create. `priceClass` decides which edge locations serve
the site.

`errorResponses` decides what a missing path returns, and it applies to the whole distribution. A
closed bucket reports a missing file as `403`, so a content site maps both `403` and `404` to a real
`404` carrying its error page, as above.

`AwsCloudFrontInvalidationServiceModule` takes a distribution and one bucket it serves, and drops
what the edge locations hold for that bucket every time its files change. Without it CloudFront
keeps serving the previous version of a file for as long as its cache policy says, which is a day:
the upload succeeds and the site does not change. It runs after the files are uploaded, because it
waits for both the distribution and the bucket.

Two things about the DynamoDB module are worth knowing before you use it, and its generated
definition file says both: a global secondary index can be added to or removed from a live table,
and a local secondary index cannot, so changing one recreates the table.

`AwsDynamoDBGlobalServiceModule` takes the table's own service and a replica per further region,
each one a region node and optional tags. A replica cannot name the region the table sits in.
Regions that share an AWS region share one copy of the table, so they must give it the same tags,
and a region in the table's own AWS region is served by the table itself:

```yaml
  - moduleId: accounts-global-module
    moduleClass: AwsDynamoDBGlobalServiceModule
    moduleInputs:
      dynamoDBService: "${{dynamodb-service-module.model.service}}"
      replicas:
        - region: "${{region-west-module.model.region}}"
          tags:
            Tier: data
```

`AwsEcsAlbServiceModule` has the deepest inputs in this catalog. `listeners` is a port and the
actions taken on it; `targets` is one entry per container the listener forwards to, each naming an
execution and how it is health checked. A target's `Name` is what a listener's `targetGroupName`
refers to:

```yaml
  - moduleId: qa-api-alb-module
    moduleClass: AwsEcsAlbServiceModule
    moduleInputs:
      albName: qa-api-alb
      region: "${{region-module.model.region}}"
      subnets:
        - "${{public-subnet-module.model.subnet}}"
        - "${{public-backup-subnet-module.model.subnet}}"
      listeners:
        - Port: 80
          rules: [ ]
          DefaultActions:
            - actionType: forward
              action:
                TargetGroups:
                  - targetGroupName: backend-v1-80
                    Weight: 100
      targets:
        - Name: backend-v1-80
          containerName: backend-v1
          containerPort: 80
          execution: "${{backend-v1-qa-execution-module.model.execution}}"
          healthCheck:
            HealthCheckIntervalSeconds: 30
            HealthCheckPath: /
            HealthCheckPort: 80
            HealthCheckProtocol: HTTP
            HealthCheckTimeoutSeconds: 5
            HealthyThresholdCount: 2
            Matcher:
              HttpCode: 200
            UnhealthyThresholdCount: 2
```

A load balancer bills by the hour from the moment it exists, whether or not anything reaches it.

## Filesystems and images

| Module                   | Inputs                                                        | Creates                            |
|--------------------------|---------------------------------------------------------------|------------------------------------|
| `AwsEfsFilesystemModule` | `region`, `filesystemName`                                    | EFS filesystem                     |
| `AwsEcrImageModule`      | `imageFamily`, `imageName`, `regions`                         | ECR repository, one per region     |
| `AwsEcrImageTagModule`   | `image`, `imageTag`, `dockerfileDirectory`, `dockerfileName?` | one published image per repository |

An EFS filesystem belongs to a region; mounting it into a subnet is the subnet module's
`localFilesystems` input, which is what produces the mount target.

The two image modules are a repository and the versions inside it, declared separately.
`AwsEcrImageModule` creates the repositories and nothing else. `AwsEcrImageTagModule` takes that
module's image as its `image` input, builds the Dockerfile at `dockerfileDirectory`, and pushes the
result into every repository the image has, under `imageTag`. That directory is relative to the
project root, because it is part of what Octo commits and an absolute path would differ on every
machine. One repository is pointed at by as many tag modules as you have versions, and adding or
removing one leaves the others alone.

`imageTag` is the only input that decides what is published. A repository's tags are immutable, so
editing `dockerfileDirectory` or `dockerfileName` publishes nothing: new content is a new tag, which
is a new module. Changing the tag publishes the new one and deletes the old.

This is one of the library's two [external
resources](/docs/building-modules/create-an-external-resource), the other being the CloudFront
invalidation. Terraform has no resource that puts
an image into a registry, so Octo runs the local `docker` CLI and the ECR API itself, which means
the machine running the apply needs Docker. An execution whose deployment names an image URI Octo
published is ordered behind it, so the same run can publish a version and start something that runs
it.

## Anchors

These are the shapes the modules above publish and consume, and they are what a module of your own
needs to match to interoperate. Import a schema from `@quadnix/octo-aws-cdk/anchors/<name>/schema`,
where `<name>` is the anchor's own name rather than the directory it sits in:
`anchors/aws-iam-role/schema`, not `anchors/aws-iam/schema`.

| Anchor                                        | On                | Publishes                                                                    |
|-----------------------------------------------|-------------------|------------------------------------------------------------------------------|
| `AwsAccountAnchorSchema`                      | account           | `awsAccountId`                                                               |
| `AwsRegionAnchorSchema`                       | region            | `awsRegionId`, `awsRegionAZs`, `regionId`, `vpcCidrBlock`                    |
| `AwsServerlessRegionAnchorSchema`             | region            | `awsRegionId`, `regionId`, `serverless`                                      |
| `AwsSubnetAnchorSchema`                       | subnet            | `subnetName`, `CidrBlock`, `AvailabilityZone`, `awsAccountId`, `awsRegionId` |
| `AwsSubnetLocalFilesystemMountAnchorSchema`   | overlay           | `subnetName`, `filesystemName`, `awsAccountId`, `awsRegionId`                |
| `AwsEcsServerAnchorSchema`                    | server            | `serverKey`, `deploymentType`                                                |
| `AwsIamRoleAnchorSchema`                      | server            | `iamRoleName`                                                                |
| `AwsSecurityGroupAnchorSchema`                | server, execution | `securityGroupName`, `rules`                                                 |
| `AwsS3StorageServiceAnchorSchema`             | service           | `bucketName`, `awsAccountId`, `awsRegionId`, `contentDigest`                 |
| `AwsS3StorageServiceAccessPrefixAnchorSchema` | service           | `accessPrefix`, `bucketName`                                                 |
| `AwsEcsClusterAnchorSchema`                   | environment       | `clusterName`, `environmentVariables`                                        |
| `AwsEcsExecutionAnchorSchema`                 | execution         | `desiredCount`, `environmentVariables`                                       |
| `AwsEcsServiceAnchorSchema`                   | overlay           | `executionId`                                                                |
| `AwsEcsTaskDefinitionAnchorSchema`            | deployment        | `cpu`, `memory`, `image`                                                     |
| `AwsEcrImageAnchorSchema`                     | image             | `imageId`                                                                    |
| `AwsEcsAlbAnchorSchema`                       | service           | `albName`                                                                    |
| `AwsCloudFrontAnchorSchema`                   | service           | `awsAccountId`, `distributionName`                                           |
| `AwsDynamoDBAnchorSchema`                     | service           | `TableName`                                                                  |
| `AwsDynamoDBGlobalAnchorSchema`               | service           | `TableName`                                                                  |
| `AwsEfsAnchorSchema`                          | filesystem        | `filesystemName`                                                             |

Two of them sit on an overlay rather than on a model, because what they describe is a relationship:
a filesystem mounted into a subnet, and an execution's ECS service.

The one you will meet first is `AwsRegionAnchorSchema`. Almost every module in this catalog takes a
region, and what it actually requires is any node named `region` that publishes that shape, which is
why [replacing the region module](/docs/using-octo/composing-modules#replacing-a-module) changes
nothing downstream.
