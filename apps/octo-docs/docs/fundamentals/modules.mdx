title: Modules
---

Every company answers the same questions in its own repository. What is a region made of. What does
a server need before it can run. What it takes to stand up a static site. The answers are good, they
took real work, and they do not travel: copying a folder of Terraform from another team means taking
on their account layout and their naming rules along with their code, because a module's contract
with its caller is a list of strings and nothing checks them against your world.

A **module** is Octo's unit of reuse. It declares the inputs it accepts, builds
[models](/docs/fundamentals/models) when it runs, and finds what other modules built by matching on
shape rather than by importing their classes. Two modules from two libraries compose without either
author having planned for it.

The shop is four of them: an app module, an account module, a region module, and a storage module,
with a server module added later. Each one is a line in `octo.yaml`:

```yaml
modules:
  - moduleId: receipts-module
    moduleClass: AwsS3StorageServiceModule
    moduleInputs:
      region: "${{region-module.model.region}}"
      bucketName: "${env.RECEIPTS_BUCKET_NAME}"
      accessPrefixes:
        - uploads
```

## The inputs are the contract

A module declares what it accepts, and the declaration is checked before the module runs. `region`
there is not a string that looks like a region ID. It is the region node itself, and the storage
module's requirement is that whatever arrives publishes AWS region details, which is what lets it
work out the account and region to put the bucket in without being told.

So a mistake in `octo.yaml` fails while modules are still composing, with a message naming the
input, rather than three layers down while Terraform is being written. Optional inputs get their
defaults at the same point. [Validation](/docs/techniques/validation) covers the rules a module
author can put on an input, and [The Definition File](/docs/using-octo/the-definition-file) covers
writing the YAML.

A module that cannot satisfy what it was asked for stops there too. Ask the shop's server module for
access to a prefix the receipts bucket does not have, and it says so before anything exists. The
alternative is finding out partway through an apply with half a stack standing.

## Order

The `moduleId` is yours to pick, and it does two things: it scopes everything that instance
produces, and it names the folder that instance generates. Load the same class twice under two IDs
and you get two independent instances, which is how the shop would get several subnets out of one
subnet module.

Modules run in the order the definition file lists them, and that order matters for one reason: a
module can only be handed something an earlier module has already built. The region module runs
before the storage module because the storage module is handed the region. Instances of one class
run together, where the first of them is listed, so whatever any of them is handed has to be listed
above the first one.

What happens in what order during an apply is decided by the
[dependencies](/docs/fundamentals/dependencies) between nodes, not by this list. Module order
decides who can see whom.

## Where a swap stops

Everything one instance produces lands in one folder of generated Terraform, and that boundary is
also the boundary of a replacement. Swap the shop's single-availability-zone region module for one
that spreads across three, and what changes is the contents of `region-module/`. Nothing else in the
definition file moves, as long as the new module publishes the same region
[anchor](/docs/fundamentals/anchors).

[Composing Modules](/docs/using-octo/composing-modules) covers what that looks like in practice, and
[Create a Module](/docs/building-modules/create-a-module) covers writing one.
