---
title: State Providers
---

Octo's [state](/docs/fundamentals/state) is three JSON files and a Terraform state file per module,
and where they live decides who can run your infrastructure. On a laptop, one person can. In a
repository, whoever has the repository can, as long as they take the lock.

A **state provider** is what makes that choice. It holds the files, it holds Terraform's own state,
and it holds the lock that keeps two runs from writing at once. Three ship with Octo, and
`settings.stateProvider` picks one.

## The three that ship

```yaml title="octo.yaml"
settings:
  stateProvider:
    type: LocalStateProvider
    statePath: .octo
```

`LocalStateProvider` writes plain JSON into a directory. Readable, diffable, and the right choice
while you are learning.

What those files hold decides how far that choice travels. Octo records every Terraform output it
maps to a resource, whatever that output is, and `resources-actual.json` is a file a project
commits: a module that creates a credential and returns it as part of a resource's response puts it
there in plain text. Nothing in `@quadnix/octo-aws-cdk` returns one today, which is a fact about
those modules rather than about the file. Terraform's own state, which sits in the same directory,
has always worked this way and holds every attribute a provider returned rather than only the
outputs Octo maps. Reports are the exception and need nothing done to them: the renderer prints
`(sensitive)` in place of any value Terraform marked, and the scaffolded `.gitignore` excludes the
directory they are written to.

`LocalEncryptionStateProvider` writes the same files encrypted, with an `.enc` suffix, and takes an
`encryptionKey`. The point is that the result is safe to commit, which gives a small team shared
state with nothing to run:

```yaml
settings:
  stateProvider:
    type: LocalEncryptionStateProvider
    encryptionKey: "${env.OCTO_STATE_ENCRYPTION_KEY}"
    statePath: .octo
```

Keep the key out of the file. Declare it under `env` and let the shell supply it.

The suffix lands on every file, Terraform's state included, so what you commit is
`<moduleId>.tfstate.enc` rather than `<moduleId>.tfstate`. The scaffolded `.gitignore` re-includes
both, because the `*.tfstate*` rule that excludes Terraform's working copies would otherwise catch
the encrypted state as well. Committing state that a run cannot find is the failure that rebuilds
infrastructure you already have, so it is worth confirming with `git status --ignored` after your
first apply.

`TestStateProvider` keeps everything in memory, and is what the test harness uses.

Where a team needs state somewhere neither local provider reaches, the arrangement that works today
is `LocalStateProvider` with the state directory on shared storage, or
`LocalEncryptionStateProvider` with the files committed to the repository.

## It holds the lock

Octo's state has one writer at a time, and the provider is what enforces it.

`octo lock` takes the lock and prints an ID. `octo apply` and `octo commit` each present that ID,
and the commit releases it. `generate` and `validate` never touch any of this, because neither
writes shared state. A second run that tries to take a held lock fails immediately, naming the ID
that holds it, before it reads state or plans anything.

The two local providers keep the lock as a file beside the state, `local-state.lock`, created
exclusively so that of two runs racing for it exactly one wins. The ID is what proves ownership:
every check compares against the ID that was handed out, so one run can never release another's
lock, and a caller holding a stale ID is told it is stale rather than told the app is free.

There is deliberately no timeout. A lock that expires mid-apply would let a second apply start while
the first might still be running, and from outside you cannot tell whether a dead run applied
nothing, everything, or half of it. A stuck lock is the correct outcome, and `octo unlock --force`
is the way out once a human has looked.

## It holds Terraform's state too

Terraform keeps its own record of what exists, and by default a local backend leaves it in the
generated module folder, where only the machine that ran the apply can see it. That is the one file
Octo cannot rebuild: lose it and Terraform plans to create infrastructure that is already there.

So it goes through the provider as well. Before any Terraform command, Octo writes each module's
state from the provider into its folder; after the command returns, whether it succeeded or failed,
it writes what the folder now holds back, under `<moduleId>.tfstate`. A long apply is also checked
in on a timer, so a runner killed halfway through loses at most a minute of record rather than all
of it.

Two consequences worth knowing:

- A module whose folder holds no state, or state recording no resources, is **deleted** from the
  provider rather than written. That is a module Terraform has destroyed.
- A module the provider holds nothing for keeps whatever its folder already has. That is what adopts
  the state of a stack which has been running with a local backend until now: the first check-in
  hands it over, and from then on the provider is the one that answers.

Point `remote_state` at a backend of your own and Terraform stops writing the file Octo checks in,
which is fine, because the two arrangements are alternatives, not layers.

## What a provider does not do

**It does not version anything.** Octo writes each file whole, every time, and keeps no history.
Being able to go back has to come from wherever the files live: a repository's history for state you
commit, or versioning on the storage the directory sits on.
